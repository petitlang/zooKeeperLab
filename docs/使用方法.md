# ZooKeeper 实验使用方法

已实际启动五个独立 Java 进程和交互式客户端，验证写入、两人猜数、平局、边界值、Leader 强制停止、重新选举、原节点重启追赶、少于多数派时拒绝提交，以及恢复多数派后使用原请求 ID 重试。

本次演练使用端口 15501–15505 和 target/manual-walkthrough 下的独立数据目录，没有改动原 data 目录。完整结果见 [实机演练记录](evidence/manual-walkthrough/summary.txt)；客户端输入输出见同目录 client-A.txt 等文件。演练启动的进程已全部停止，以下常规操作使用 5001–5005。

## 1. IntelliJ IDEA 启动配置

打开 D:/zooKeeperLab，等待 Maven 导入与编译完成。在顶部运行配置下拉框选择以下名称，每个配置运行一次，保留其控制台。

| 运行配置 | Main class | Program arguments | 用途 |
| --- | --- | --- | --- |
| ZooKeeper Node 1 | fr.isep.node.NodeServer | --id 1 | 节点 1，端口 5001 |
| ZooKeeper Node 2 | fr.isep.node.NodeServer | --id 2 | 节点 2，端口 5002 |
| ZooKeeper Node 3 | fr.isep.node.NodeServer | --id 3 | 节点 3，端口 5003 |
| ZooKeeper Node 4 | fr.isep.node.NodeServer | --id 4 | 节点 4，端口 5004 |
| ZooKeeper Node 5 | fr.isep.node.NodeServer | --id 5 | 节点 5，端口 5005 |
| ZooKeeper Client A | fr.isep.client.ClientApp | --node 4 --client A | 设置目标，连接节点 4 |
| ZooKeeper Client B | fr.isep.client.ClientApp | --node 3 --client B | 第一位猜数者，连接节点 3 |
| ZooKeeper Client C | fr.isep.client.ClientApp | --node 5 --client C | 第二位猜数者，连接节点 5 |

所有配置的 Working directory 为 D:/zooKeeperLab。共享配置已写入 .run 目录。不要继续使用主类 fr.isep.Node 的旧配置，也不要将程序参数只写成数字 2；正确格式是 --id 2。

启动全部五个节点后再启动三个客户端。等待节点控制台出现 LEADER ready，并在客户端输入 read 确认 ready=true。每个 JVM 是一个节点，不能把五个节点当成一个运行配置来回替换运行。

## 2. 答辩演示顺序

下列数字轮次假设从空日志开始；已有数据时轮次会继续累加。不要为了恢复演示删除日志。

| 步骤 | 在哪里操作 | 输入或动作 | 预期现象及解释 |
| --- | --- | --- | --- |
| 1 | A 客户端 | read | 显示 leader、ready、target、round；全新集群 target=unset |
| 2 | A 客户端 | write 50 | REQUEST_COMMITTED，目标变为 50；Leader 输出 PROPOSE、ACK、COMMIT |
| 3 | B 客户端 | guess 30 | REQUEST_ACCEPTED，guesses=1/2，目标仍为 50 |
| 4 | B 客户端 | retry | 仍为 1/2；相同请求不会重复计人数 |
| 5 | C 客户端 | guess 62 | 第二个不同客户端触发结算；62 距离 50 更近，提交目标 62，轮次加一 |
| 6 | A 客户端 | read | 确认目标 62，并记下 leader 的实际编号；Follower 本地读取可能短暂落后 |
| 7 | 对应 Leader 的节点控制台 | 点击 IDEA 的 Stop，强制停止该节点进程 | 等待心跳超时、重新选举和日志恢复；不要把客户端控制台当作节点停止 |
| 8 | 存活客户端 | read，等待新 leader 且 ready=true | 本次实际从 Leader 1 切换为 2，已提交目标得到保留；其他历史下编号可能不同 |
| 9 | 客户端（若其连接的节点也被停止） | connect 2（按实际存活节点替换 2） | 只切换这个客户端的连接，保留待重试请求；客户端不自动切换节点 |
| 10 | A 客户端 | write 40 | 新 Leader 能继续提交写入 |
| 11 | B、C 客户端，依次 | B: guess 39；C: guess 80 | 两人猜数继续工作，目标变成 39 |
| 12 | 被停止的节点配置 | 用同一 --id、同一 data-dir 再次 Run | 节点读取原日志，作为 Follower 重新加入并自动追赶，不需要再次写入 |
| 13 | 原 Leader 恢复后的节点 | 让一个客户端 connect 到此节点，再 read | 最终 ready=true，目标追赶到 39 |

每轮必须由两个不同 client ID 提交。B 连续猜两次不算两个人；同一轮换一个请求再次猜测会被拒绝。Write 不算猜测人数。没有三秒倒计时：第一人提交后会一直等第二人。平局时选择 Leader 先收到的猜测。

## 3. 客户端命令速查

| 命令 | 示例 | 含义 |
| --- | --- | --- |
| write N | write 50 | 通过完整复制流程设置目标；成功后旧轮次未结算的猜测失效 |
| guess N | guess 62 | 先读取当前轮次，再提交本轮猜测；数值必须为 0–100 |
| read | read | 读取当前所连节点的本地已提交状态，可能暂时落后 |
| retry | retry | 重发当前客户端保留的同一请求 ID、值和轮次；不创建新请求 |
| connect NODE | connect 2 | 选择连接节点 2；NODE 是节点编号 1–5，不是端口号 |
| help | help | 显示可用命令 |
| quit | quit | 正常关闭客户端；节点进程会继续运行 |

成功提交后会清除当前保留请求。ACCEPTED、UNCERTAIN 或 REJECTED 后仍保留请求；下一条新的 write/guess 命令会替换它。已经落盘但结果不确定的请求，应先 read，再 retry；不要以新的 write 命令冒充同一次重试。

## 4. 返回状态怎么看

| 输出 | 意思 | 下一步 |
| --- | --- | --- |
| REQUEST_ACCEPTED | 猜测已收集，但尚未提交新目标 | 等另一名客户端猜测；可通过相同请求 retry 核实 |
| REQUEST_COMMITTED | 操作已在多数派复制后形成持久提交 | read 查看结果；Follower 可能短暂追赶中 |
| REQUEST_REJECTED | 该请求未被本次调用接受，如重复客户端、旧轮次、无就绪 Leader | 阅读提示；确认状态后决定重试或发起新操作 |
| REQUEST_UNCERTAIN | 结果需核实，未决提案可能在恢复中提交 | read，再使用原请求 retry |
| ready=false | 该节点尚未准备好处理正常请求 | 等选举/同步完成，或 connect 到已就绪节点 |
| RPC UNAVAILABLE | 连接的节点可能停止或不可达 | connect 到存活节点，再 read/retry |

guesses 进度保存在 Leader 内存里。Guess 的转发响应会显示 Leader 进度；Follower 的本地 read 不会展示 Leader 的实时猜测集合。还未形成持久提案的猜测可能在 Leader 崩溃后丢失，需要读取恢复后的轮次并重新提交。

## 5. PowerShell 替代 IDEA

先在 D:/zooKeeperLab 执行 ./scripts/build.ps1。然后分别在不同终端执行：

| 终端 | 命令 |
| --- | --- |
| 节点 1–5，各一个终端 | ./scripts/run-node.ps1 -Id 1（依次替换为 2、3、4、5） |
| 客户端 A | ./scripts/run-client.ps1 -Node 4 -Client A |
| 客户端 B | ./scripts/run-client.ps1 -Node 3 -Client B |
| 客户端 C | ./scripts/run-client.ps1 -Node 5 -Client C |
| 一次性读取 | ./scripts/run-client.ps1 -Node 2 -Client inspect -Command 'read' |

若 PowerShell 执行策略阻止本地脚本，可在当前终端执行 Set-ExecutionPolicy -Scope Process Bypass。

## 6. 多数派故障的进阶演示

固定五个节点的多数派始终是 3。保留 Leader 和一个 Follower，停止另外三个节点；write 100 会返回 UNCERTAIN，原目标保持不变。重启一个原节点，恢复到至少三个进程后，在原客户端输入 retry；相同请求可完成提交。重启剩余节点，等待它们追赶。

本次实际验证：仅剩 2/5 时目标保持 39；恢复 3/5 后相同请求提交目标 100；最后五个节点均 ready=true 且 target=100。

关闭演示时先在各客户端输入 quit，再停止各节点。停止节点不会删除日志；后续重启要使用同一节点编号与数据目录。
