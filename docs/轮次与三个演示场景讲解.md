# ZooKeeper 实验：轮次与三个演示场景

游戏规则、日志编号及三个实验场景的复习笔记。启动配置与命令见 [使用方法](使用方法.md)。

## 1. 客户端与节点

系统中有两类参与者：

| 参与者 | 做什么 |
| --- | --- |
| 客户端 A、B、C 等 | 输入 `write`、`guess`、`read`，参与游戏 |
| 五个服务器节点 | 保存日志、复制数据、提交目标值、选举 Leader |

五个节点中，一个是 Leader，另外四个是 Follower。客户端可以连接任意节点；Follower 收到写入或猜测请求后，会转发给 Leader。

**客户端负责参与游戏；节点负责可靠保存游戏结果。**客户端 ID 与节点 ID 是两回事。

## 2. 游戏轮次 round 怎么算

**`round` 表示当前正在围绕哪个目标值进行猜测。只有新目标提交成功，轮次才加 1。**

假设从全新的数据目录开始：

| 操作 | 当前目标 target | 游戏轮次 round | 原因 |
| --- | --- | --- | --- |
| 节点刚启动，尚未设置目标 | 未设置 | 0 | 游戏还没有开始 |
| A 输入 `write 50`，提交成功 | 50 | 1 | 有了第一轮目标 |
| B 输入 `guess 30` | 50 | 1 | 只有一个人猜，尚未结算 |
| C 输入 `guess 62`，结算并提交成功 | 62 | 2 | 62 成为下一轮目标 |
| B 对新目标输入 `guess 60` | 62 | 2 | 只有一个人猜，仍在第二轮 |
| C 输入 `guess 70`，结算并提交成功 | 60 | 3 | 60 更接近 62，成为第三轮目标 |

不是每输入一次命令就加一轮，也不是每个人猜一次就加一轮。

### 当前项目的具体规则

- 每轮收到 **2 个不同客户端 ID** 的有效猜测后自动结算。
- 没有倒计时；第一人提交后，会继续等待第二人。
- 每个客户端每轮只能提交一个猜测；相同请求重试不重复计人数。
- 两个猜测都与这一轮原来的目标比较。
- 与目标的绝对距离最小者获胜；距离相同时，选择 Leader 先收到的猜测。
- 获胜值完成复制并提交成功后，才成为新目标，轮次加 1，猜测集合清空。
- 直接执行新的 `write`，成功提交后也会开启下一轮，旧轮次尚未结算的猜测失效。
- 数值范围为 0–100，包含 0 和 100。

题目没有规定收集人数和距离相同时的处理方式；本项目选择固定两人，并按到达顺序处理平局。

### 例子：目标 50，猜测 30 和 62

| 猜测 | 计算方式 | 与目标的距离 |
| --- | --- | --- |
| 30 | `abs(30 - 50)` | 20 |
| 62 | `abs(62 - 50)` | 12 |

62 的距离更小，因此获胜。

注意：B 猜 30 后，目标仍然是 50。C 猜 62 时，也与 **50** 比较，不是与 B 的猜测 30 比较。

### 容易忽略的情况

| 情况 | round 是否增加 |
| --- | --- |
| 读取状态 `read` | 不增加 |
| 收到第一人的猜测 | 不增加 |
| 第二人提交，但获胜提案尚未提交成功 | 不增加 |
| 获胜提案提交成功 | 增加 1 |
| 新的 `write 50` 提交成功，而原目标恰好也是 50 | 仍增加 1；这是一次新的目标提交 |
| 用相同请求 ID 重试一个已提交的请求 | 不重复增加 |
| 单纯发生 Leader 更换 | 不增加，也不归零 |
| 恢复时把一个未决提案补充提交 | 随该次提交增加 |

已有日志时，轮次会从持久化状态继续，不一定从 0 开始。重新打开客户端也不会重置游戏轮次。

## 3. round、epoch、seq 的区别

| 字段 | 代表什么 | 什么时候变化 |
| --- | --- | --- |
| `round` | 游戏轮次 | 新目标成功提交时加 1 |
| `epoch` | Leader 任期编号 | 建立新 Leader 任期时增加 |
| `seq` | 当前任期内的提案序号 | Leader 创建新的提案时增加 |

日志用 **`(epoch, seq)`** 标识一条提案。

客户端输出的 `last=1:2`，表示最后提交的提案编号是 `(epoch=1, seq=2)`，不直接表示游戏轮次。

### 连贯的例子

下面假设从空日志开始，过程中没有额外未决提案：

| 事件 | 当前 epoch | 提案或最后提交编号 | 游戏 round |
| --- | --- | --- | --- |
| 第一个 Leader 就绪 | 1 | 暂无；seq 准备值为 0 | 0 |
| `write 50` 提交 | 1 | `(1,1)` | 1 |
| B 猜 30 | 1 | 最后提交仍是 `(1,1)` | 1 |
| C 猜 62，获胜值提交 | 1 | `(1,2)` | 2 |
| Leader 崩溃，新 Leader 恢复完成 | 2 | 最后提交仍是 `(1,2)` | 2 |
| 新 Leader 执行 `write 40` 并提交 | 2 | `(2,1)` | 3 |

新任期的 seq 重置为 0，第一条新提案使用 seq=1。旧日志仍保留原来的编号，不会全部改成新 epoch。

`seq` 在创建提案时就增加，`round` 在提交成功时才增加。因此，一个尚未提交的提案可以已经有编号，但目标和轮次仍保持原值。相同请求的重试会复用原提案编号。

## 4. 猜数人数与提交多数派

| 数字 | 用途 | 参与者 |
| --- | --- | --- |
| 2 | 决定何时结束收集猜测 | 两个不同的客户端 |
| 3/5 | 决定提案能否提交 | 五个服务器节点中的多数派 |

多数派可以由 **Leader 自己的一份持久日志 + 至少两个 Follower 的确认**组成。

不需要等全部五个节点确认，但不能把多数派理解成“两个客户端猜完就已经提交”。猜数收集完成后，仍必须执行底层复制与提交。

## 5. 场景一：正常写入 Normal write flow

### 验证目标

客户端设置的目标能够通过多数派复制形成持久提交，而不是只保存在接收请求的那个节点。

### 操作与内部流程

假设客户端 A 连接节点 4，实际 Leader 是节点 1：

| 步骤 | 谁做什么 | 目标是否改变 |
| --- | --- | --- |
| 1 | A 输入 `write 50`，请求到达节点 4 | 不改变 |
| 2 | 节点 4 是 Follower，将请求转给 Leader | 不改变；转发本身不会记录提案 |
| 3 | Leader 创建例如 `(1,1)` 的提案，持久保存，并向 Followers 发送 `PROPOSE` | 不改变 |
| 4 | Followers 将提案保存为 `PROPOSED`，持久落盘后回复 ACK | 不改变 |
| 5 | Leader 确认至少 3 个不同节点已持久保存，保存本地 COMMIT 并广播 `COMMIT` | Leader 提交后改变 |
| 6 | Followers 收到 COMMIT，持久保存并应用 | 各节点陆续变为 50 |

### PROPOSED 和 COMMITTED

| 状态 | 含义 | 能否作为新的可见目标 |
| --- | --- | --- |
| `PROPOSED` | 提案已保存，但还没有形成提交 | 不能 |
| `COMMITTED` | 已形成持久提交 | 可以 |

ACK 的含义是“我已经持久保存了这条提案”，不是“我已经把目标改好了”。

### 观察结果

- 客户端：出现 `REQUEST_COMMITTED`，目标显示为 50。
- Leader 控制台：出现 `PROPOSE → ACK → COMMIT`。
- 其他节点：收到 COMMIT 或完成追赶后，也能读到 50。

题目中的“所有客户端看到新目标”不是指所有节点在同一个瞬间更新。当前 Read 是本地读取，Follower 在收到提交或完成同步之前可能短暂显示旧值。

## 6. 场景二：猜数 Guessing flow

### 验证目标

游戏选出的获胜值也经过完整复制与提交，才能成为下一轮目标。

### 操作与内部流程

| 步骤 | 操作 | 系统行为 |
| --- | --- | --- |
| 1 | 当前目标为 50 | 当前轮围绕 50 猜数 |
| 2 | B 输入 `guess 30` | Leader 收集第一个猜测，返回 `REQUEST_ACCEPTED`，进度 `1/2` |
| 3 | C 输入 `guess 62` | 收齐两个不同客户端的猜测 |
| 4 | Leader 比较距离 | 62 比 30 更接近 50 |
| 5 | Leader 为获胜值 62 创建 GUESS 提案 | 执行 `PROPOSE → ACK → COMMIT` |
| 6 | 提交成功 | 目标变为 62，round 加 1，猜测人数清零 |

Follower 收到 Guess 时也会转发给 Leader；只有 Leader 维护这一轮的猜测集合。

### ACCEPTED 不等于 COMMITTED

| 返回状态 | 含义 |
| --- | --- |
| `REQUEST_ACCEPTED` | 猜测已收集，新目标尚未提交。 |
| `REQUEST_COMMITTED` | 本轮结果已提交。 |
| `REQUEST_REJECTED` | 本次调用拒绝了请求，原因见返回信息。 |
| `REQUEST_UNCERTAIN` | 结果需要核实，先读取状态，再用原请求重试。 |

相同请求使用 `retry` 不会多算一个人。B 在同一轮另发一个新的猜测，也不能代替 C，程序会拒绝同一客户端的第二个不同请求。

Guess 的转发响应会显示 Leader 的收集进度。Follower 的本地 `read` 不会重建 Leader 内存中的实时猜测集合，因此不要用 Follower Read 的 `guesses=0/2` 判断 Leader 是否已经收到了 B 的猜测。

## 7. 场景三：Leader 崩溃与恢复 Leader crash and recovery

### 验证目标

负责协调的进程停止后，其余节点可以选出新 Leader，恢复日志，并继续处理操作；已经提交的目标不能丢失或回退。

### 操作与内部流程

| 步骤 | 发生什么 | 重点 |
| --- | --- | --- |
| 1 | 停止实际 Leader 的 Java 进程 | 其他节点继续运行 |
| 2 | Followers 超时收不到心跳 | 开始选举，不是停止瞬间就完成切换 |
| 3 | 比较各节点最新日志的 `(epoch, seq)` | 包括尚未提交的 PROPOSED 提案 |
| 4 | 确定候选胜者 | 先比 epoch，再比 seq；都相同时选节点 ID 最小的 |
| 5 | 新 Leader 整理并同步日志，处理未决提案 | 保留已提交历史，恢复前不开放正常写入 |
| 6 | 新任期建立、恢复完成，显示 `ready=true` | 后续新提案使用新 epoch，seq 从 1 开始 |
| 7 | 客户端继续 Write、Guess | 游戏继续，round 不因换 Leader 而归零 |
| 8 | 原 Leader 用原 ID、原数据目录重启 | 作为 Follower 加入并自动追赶日志 |

至少需要三个节点响应才能推进选举恢复。不能因为只剩两个节点，就把多数派改成两个。

实现中，新 epoch 会在恢复完成前持久保存；`ready=true` 才表示该节点已经准备好继续正常操作。只看到 Leader 编号变化，还不代表恢复一定完成。

### 选举比较例子

| 节点 | 最新日志编号 | 比较结果 |
| --- | --- | --- |
| 2 | `(1,5)` | 落后于 `(2,1)` |
| 3 | `(2,1)` | 与节点 4 的日志编号相同 |
| 4 | `(2,1)` | 节点 3 的 ID 更小，因此节点 3 优先 |

epoch 优先于 seq，因此 `(2,1)` 大于 `(1,100)`。不要只比较冒号后面的数字。

### 崩溃前的操作是否一定保留

| 崩溃前的状态 | 如何理解 |
| --- | --- |
| 猜测只存在 Leader 的内存集合里 | 可能丢失，读取恢复后的轮次后重新提交 |
| 提案只保存在旧 Leader 本地，没有达到多数派 | 可能未被新历史保留，不能认为它已经提交 |
| 未决提案被恢复算法选中 | 重新复制到多数派后可以补充提交 |
| 已经 COMMITTED | 必须保留，不能删除或回退 |

因此，“没有收到成功回复”不总等于“肯定没提交”。遇到 UNCERTAIN，应先 `read`，再使用同一个请求 ID `retry`。

### 演示时确认四件事

1. `leader` 编号确实改变。
2. 已提交的目标值被保留。
3. 新 Leader 下还能写入和猜数。
4. 原节点重启后能追赶到当前状态。

如果客户端连接的正好是被停止的节点，需要输入 `connect 2` 等命令改连存活节点。这里的 2 是节点编号，不是端口号。

**Leader 选举自动进行，客户端更换连接需要手动操作。**

## 8. 完整演示示例

假设从空日志开始，正常写入与猜数都成功：

| 操作 | 目标 | 游戏轮次 | 说明 |
| --- | --- | --- | --- |
| A：`write 50` | 50 | 1 | 场景一：正常写入 |
| B：`guess 30` | 50 | 1 | 等待第二人 |
| C：`guess 62` | 62 | 2 | 场景二：猜数结算 |
| 停止 Leader，等待新 Leader 就绪 | 62 | 2 | 场景三：恢复已提交状态 |
| A：`write 40` | 40 | 3 | 验证故障后继续写入 |
| B：`guess 39` | 40 | 3 | 等待第二人 |
| C：`guess 80` | 39 | 4 | 验证故障后继续猜数 |
| 重启旧 Leader | 39 | 4 | 原节点追赶，不凭空增加轮次 |

## 9. 复习速查

| 问题 | 回答 |
| --- | --- |
| 每条命令都会加一轮吗？ | 不会，只有新目标提交成功才加一轮。 |
| 两人猜完就必然成功吗？ | 不一定，还要完成多数派复制与提交。 |
| 两个猜测先后改变目标吗？ | 不会，它们都与本轮原目标比较。 |
| 已保存 PROPOSED 就能显示新目标吗？ | 不能，要等 COMMITTED。 |
| 需要五个节点全部 ACK 吗？ | 不需要，固定多数派为 3/5。 |
| 两个客户端和三个节点有关系吗？ | 分别用于游戏结算和数据提交，是两个不同门槛。 |
| 换 Leader 会把 round 清零吗？ | 不会，已提交游戏状态会恢复。 |
| 换 Leader 后哪些数字变化？ | epoch 增加，新任期 seq 重置；round 随实际提交变化。 |
| 为什么 read 可能看到旧目标？ | 当前读取的是所连节点的本地已提交状态，Follower 可能正在追赶。 |
| 为什么新 Leader 出来后还不能操作？ | 可能仍在恢复，等待 ready=true。 |
| 为什么重启不能删除 data？ | 恢复依赖原节点的持久日志。 |
| 故障时应该重新 write 还是 retry？ | 要重试同一次不确定操作时，先 read，再 retry 原请求。新的 write 会产生新请求。 |

答辩随机选择三个场景中的一个进行现场演示，需要掌握各步骤对应的复制、提交和恢复过程。
