# 今天这个 TP 怎么理解和答辩

## 从你以前的 TP 接上

你之前的 GrpcServer 是 `ServerBuilder.forPort(...).addService(...).build()`，
今天 NodeServer 仍然这样启动，只是每个节点有一个端口，同时提供两个 service。
你之前的 CalculatorServiceImpl 用 `request.getA()` 取参数，再 `newBuilder()`
构造返回值，最后 `onNext()` 和 `onCompleted()`。今天的 GameServiceImpl
和 CoordinationServiceImpl 完全沿用这一套。

你之前的 GrpcClient 是 channel -> blocking stub -> request -> 调用 RPC -> response。
今天 ClientApp 也是这个顺序。Scanner 的交互循环来自 SocketClient。
区别是以前只联系一个计算器服务器，今天节点之间也互相当 gRPC 客户端。
不用同时混用 Socket 和 gRPC：题目让你选一种以前学过的通信方式。

## 先掌握这五个词

- Leader：唯一负责给新操作编号、复制并提交的节点。
- Follower：接收日志；客户端找它写入时，它把请求转给 leader。
- Quorum：固定五个节点的多数是三个。leader 自己的一份也算。
- Epoch：第几代 leader。换 leader 时加一。
- Seq：这一代 leader 的第几条 proposal，从一开始，换代时先归零。

`(2,1)` 大于 `(1,100)`，因为先比较 epoch。相同 epoch 再比较 seq。
只有 tag 完全相同时，才选择 ID 更小的节点。这里千万别说成“最大 ID 获胜”。

## 为什么日志有 PROPOSED 和 COMMITTED

客户端在 follower 4 输入 write 50：

1. follower 4 只转发客户端请求，这时还不写日志。
2. leader 1 创建 `(1,1)`，在自己的文件写入 PROPOSED。
3. leader 发 Propose RPC。follower 落盘成功以后才返回 ACK。
4. leader 收到足够 ACK，连自己的日志至少三份，才 COMMIT。
5. leader 更新自己的 target，发送 Commit RPC；follower 收到后更新 target。

“有 proposal”表示这个值还在准备，不能直接对客户端显示为最新 target。
所以 `NodeState.commit()` 才更新 target 和 round。
RPC response 就是 ACK，不需要再单独做一个 ACK service。

法语可以说：
> Le follower transmet la requete au leader. Le leader attribue un tag et replique
> le proposal. Chaque follower ecrit le journal avant l'ACK. Avec trois copies
> durables sur cinq, le leader commit et diffuse le COMMIT.

## 猜数怎么算

target=50，B 猜 30，C 猜 62。距离分别是 `Math.abs(30-50)=20` 和
`Math.abs(62-50)=12`，因此选 62。把选出的 62 当作一次 GUESS 操作，
继续走相同的复制、ACK、COMMIT。不是只改 leader 的变量。

第一条 guess 到达后等三秒。这是我们为题目未规定的“何时收齐”作出的实现选择。
每个客户端一轮最多一次；相同距离选先来的。`REQUEST_ACCEPTED` 是收到了猜数，
不是已经决定结果。用 read 查看下一轮的 target。

法语：
> Je collecte les guesses pendant trois secondes apres la premiere guess.
> Je compare les distances absolues et je replique la meilleure valeur comme
> une nouvelle operation. En cas d'egalite, je garde la premiere arrivee.

## leader 被杀之后

leader 大约每 500 毫秒发送心跳。五秒加一点节点 ID 的错开时间还没收到心跳，
follower 就开始选举。比较最新日志 tag，包含 PROPOSED；同 tag 选较小 ID。
没有至少三个可联系的节点，不能开始恢复并提交。

获胜节点读取日志，检查它们是不是相同历史的前缀，保留已经 COMMITTED 的记录。
有未提交尾部时，先把选择的历史同步到多数，再按顺序完成这些 proposal。
恢复期间不接受正常写入。新 leader 把 epoch 加一并持久化，seq 归零。
旧 leader 重启后不会自动恢复 leader 身份，它等待心跳并同步成为 follower。

注意：有 PROPOSED 的值在恢复之前仍不可见。结果不确定的写入可能在恢复时提交，
所以不能把 REQUEST_UNCERTAIN 解释成“操作一定失败”。
还只在内存里排队的 guesses 没有持久化，会丢失，要重新提交。

法语：
> Les followers detectent l'absence de heartbeat. Le noeud avec le dernier tag
> le plus grand gagne ; a egalite, le plus petit ID gagne. Avant de reprendre,
> il synchronise les journaux, conserve les commits et termine la queue
> selectionnee apres replication a quorum. Il commence un nouvel epoch.

## 为什么有线程和锁

以前 SocketServer 给客户端开线程，所以你已经见过并发。
gRPC 也能同时处理多个客户端：如果两条 write 同时拿 seq，就可能重复。
`synchronized (operationLock)` 让本节点一次只执行一条写入或选举；`synchronized` 保护
NodeState 的状态和 LogStore 的日志。普通 Thread 负责心跳和三秒猜数窗口，用 Thread.sleep 等待，写法沿用你的 Socket TP。

先理解“同时访问共享变量会冲突，需要串行保护”，不必把锁讲成复杂框架。
存储类比以前的 TP 更长，因为它还处理持久化、重复请求和进程崩溃。

1. ClientApp：先看熟悉的 channel / stub / Scanner。
2. GameServiceImpl：看与 CalculatorServiceImpl 相同的请求和返回。
3. LeaderCoordinator.write：完整的五步写入流程。

## 老师常问的几个问题

**为什么三个？** 五个节点多数为三，两个多数集合至少相交一个节点。
这里保留多数复制原则，但选举是 TP 简化协议，没有实现完整 Raft/ZAB。

**为什么不能 follower 收到客户端 write 就改 target？** 会绕过 leader 和 quorum，
其他节点不知道这个改变；follower 应等 PROPOSE，再等 COMMIT。

**为什么不只用一个数字当 tag？** epoch 区分 leader 的代数，seq 区分这一代的操作。
重启要保留 epoch，否则旧 leader 的消息可能被误认为当前消息。

**Read 一定是最新的吗？** 本实现读本地已经提交的状态。落后的 follower 在同步前
可能读到旧值，不能声称是线性一致读。

**网络分区怎么办？** 这次验证的是固定五个 localhost 节点的进程崩溃和恢复。
没有完整的投票、租约或正式分区证明，不能宣称具备生产 ZooKeeper 的全部保证。

**以后两个节点掉了还能玩吗？** 还有三个时可以建立 quorum；只剩两个就不能提交。

**这是基于以前 TP 吗？**
> Oui. Je reutilise la structure du TP gRPC : ServerBuilder, ManagedChannel,
> blocking stub, messages Protobuf et StreamObserver. Le menu reprend la boucle
> Scanner du TP Socket. J'ajoute la coordination entre cinq serveurs.

## 节点进程怎么退出

NodeServer.close() 先停止接收新 RPC，再停止心跳、关闭连接，最后关闭日志。
main 和 shutdown hook 都可能调用 close，所以用一个 boolean closed 标志：
第一次清理，后面的调用直接 return。方法加 synchronized，防止同时清理。
进程专项测试检查了重复启动、端口冲突、并发关闭，以及退出后端口和日志锁能否释放。
